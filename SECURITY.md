# Security & Privacy Model

## Apsara Ice Creams × DVHIMSR Student Coupon System

This document details the security architecture, concurrency protections, data minimization, and threat mitigations implemented across the coupon system.

---

## 1. Cryptographic Token Architecture

A sequential coupon ID alone (e.g. `DVHIMSR-001`) is predictable. If redemption relied only on the coupon ID, malicious users could guess unredeemed codes.

To eliminate this vulnerability:
1. **Dual Credential Design**:
   - `Coupon ID`: Human-readable identifier (`DVHIMSR-001`) for display on bills and store records.
   - `Token`: High-entropy 64-character SHA-256 random hex string generated by Google Apps Script:
     ```javascript
     var raw = Utilities.getUuid() + "-" + new Date().getTime() + "-" + Math.random().toString(36);
     var digest = Utilities.computeDigest(Utilities.DigestAlgorithm.SHA_256, raw, Utilities.Charset.UTF_8);
     ```
2. **QR Code Verification**:
   - The dynamic coupon QR encodes the secure redemption URL with the token.
   - Redemption requests must present the valid `token`. Guessing a 64-character hex token is cryptographically infeasible ($16^{64}$ combinations).

## 2. Server-Side Concurrency & Race Condition Elimination

### Critical Section Protection (`LockService`)
Google Apps Script operates across distributed nodes. Without locks, concurrent requests can cause two critical race conditions:
1. **Coupon ID Collision**: Two simultaneous requests reading the same "last row" and allocating `DVHIMSR-015` twice.
2. **Double Redemption Race**: Two shop attendants scanning the same coupon at the exact same millisecond.

### Implementation:
Every mutation in [`CouponService.gs`](file:///e:/MBA/apps-script/CouponService.gs) and [`RedemptionService.gs`](file:///e:/MBA/apps-script/RedemptionService.gs) is shielded by:
```javascript
var lock = LockService.getScriptLock();
var hasLock = lock.tryLock(30000); // Wait up to 30 seconds
```
Inside the locked critical section:
- Status is re-read directly from the spreadsheet.
- State is verified (`UNUSED`).
- Status is updated to `USED` before releasing the lock.
- **Result:** Simultaneous scans always resolve to **1 SUCCESS** and **all others REJECTED (`ALREADY_USED`)**.

## 3. Idempotency & Repeat Claim Discipline

### Duplicate Claim Protection
- Mobile connections frequently drop or duplicate packets.
- The client creates a unique UUID `claimRequestId`.
- Apps Script checks whether this `claimRequestId` already exists.
- If it does, Apps Script returns the already-created coupon rather than incrementing the counter.

### Repeat Claims Permitted
- The system **does not fingerprint devices, IP addresses, or browser cookies**.
- A student scanning the poster QR on a different day starts a new session with a new `claimRequestId` and receives the next valid coupon.

---

## 4. Privacy & Data Minimization

In compliance with modern privacy principles:
- **Zero Student PII**: No names, email addresses, phone numbers, student ID cards, or location coordinates are collected, requested, or stored.
- **Zero Third-Party Trackers**: No analytics trackers, Facebook pixels, or advertising SDKs.
- **Zero Credentials**: No login accounts, passwords, or authentication cookies.

---

## 5. Formula Injection & Input Sanitization

Any user input submitted to the Google Sheets backend is passed through:
```javascript
sanitizeText: function(input) {
  var str = String(input).trim();
  if (/^[=+\-@]/.test(str)) {
    str = "'" + str; // Neutralize spreadsheet formula execution
  }
  return str;
}
```
This prevents formula injection attacks (e.g. `=IMPORTXML(...)`) inside Google Sheets.

---

## 6. Token Redaction in Public Interfaces

- The Admin dashboard endpoints (`action=stats`, `action=recent`, `action=search`) intentionally **omit the redemption token**.
- Only the Google Sheet owner with authorized Google account access can view the raw `Coupons` sheet.
